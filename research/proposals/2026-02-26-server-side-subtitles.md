## 🔬 Researcher: Server-Side Burned-In Subtitles via FFmpeg

### 🎯 Executive Summary
Propose an architecture to support automatic burned-in subtitles for generated highlight videos using FFmpeg's `subtitles` filter on the server.

### 💡 Problem Statement
**Current situation:**
The application generates clips and text transcripts but lacks the ability to burn subtitles directly into the video file (burned-in or "hardcoded" subtitles), which are extremely popular and necessary for viral short-form content (TikTok, Reels, Shorts).

**User impact:**
Users have to use a secondary video editing tool (like CapCut) to add subtitles to the videos generated by AudioHighlights.

**Example scenario:**
A podcaster generates a 60-second highlight about a controversial topic but needs to post it on Instagram where users watch with sound off. They have to manually import the video and SRT file into another tool.

### 🚀 Proposed Solution
**What:**
A new feature to burn the generated SRT subtitle directly into the output MP4 during the video cut or concatenation phase using our existing `ffmpeg-service`.

**How it works:**
1. Update `ffmpeg-service` to accept an `.srt` file payload or string alongside the video processing request.
2. In `ffmpeg-service`, use the `-vf subtitles=file.srt` filter to process the video.
3. This requires re-encoding the video (we can't use `-c copy` for the video stream if we are applying a video filter), so we will provide this as an optional "Burn Subtitles" toggle for users who prioritize having subtitles over fast stream copying.

**Why this approach:**
- `ffmpeg-static` already has `libass` and `fontconfig` enabled.
- We verified with a POC that the `subtitles` filter works successfully with the installed FFmpeg binary.
- This leverages our existing microservice architecture without adding massive client-side load (WASM FFmpeg is too slow for re-encoding video with subtitles and often lacks `libass`).

### 📊 Research Findings

**Technology Analysis:**
- **Library/Framework:** FFmpeg (`subtitles` filter via `libass`)
- **Maturity:** Stable
- **Adoption:** Industry standard for hardcoding subtitles
- **License:** GPL (covered by our ffmpeg-static usage)

**Best Practices:**
- Re-encoding requires careful bitrate and preset selection to balance speed and quality. Using `-preset fast` or `-preset veryfast` can mitigate the delay compared to `-c copy`.

### 🧪 Proof of Concept

**Implementation:**
```javascript
import cp from 'child_process';
import ffmpegStatic from 'ffmpeg-static';

const testInput = 'input.mp4';
const testSub = 'test.srt';
const testOutput = 'output.mp4';

// Use subtitles filter to hardcode subtitles
cp.execSync(`${ffmpegStatic} -i ${testInput} -vf "subtitles=${testSub}" -y ${testOutput}`);
```

**Performance:**
- Before: Stream copy (instantaneous)
- After: Full video re-encoding (takes roughly 0.5x to 1x the duration of the clip)
- Impact: Processing time increases, but adds significant value. This should be strictly optional.

### 📈 Value Proposition

**Benefits:**
- ✅ Increases the virality of exported clips natively
- ✅ Saves users time by removing the need for third-party editors
- ✅ Creates a fully "ready to post" asset

**User stories:**
- As a creator, I can generate a clip with burned-in subtitles so that I can directly post it to Instagram Reels without extra editing.

### ⚖️ Trade-offs

**Pros:**
- ✅ High value add for social media creators
- ✅ Keeps users entirely within our ecosystem

**Cons:**
- ❌ Re-encoding takes significantly longer than stream copying and increases server CPU usage.
- ❌ Requires passing the SRT file to the ffmpeg-service.

**Alternatives considered:**
| Alternative | Pros | Cons | Decision |
|-------------|------|------|----------|
| Client-side WASM | Offloads CPU from server | Very slow, often lacks `libass` | Not chosen due to technical limitations |
| WebCodecs API | Fast, modern | Highly complex to implement font rendering over video frames | Too complex for current iteration |

### 🛠️ Implementation Plan

**Phase 1: Foundation** (estimated: 1 day)
- Update `ffmpeg-service` API to accept `srtContent` alongside video cuts.
- Implement temporary file handling for the `.srt` file.

**Phase 2: Core Feature** (estimated: 2 days)
- Update `ffmpegArgs` logic to conditionally use `-vf subtitles=temp.srt` and switch from `-c copy` to a fast h264 encoder preset when subtitles are requested.

**Phase 3: Polish & Testing** (estimated: 1 day)
- Add "Burn Subtitles" toggle in the UI (disabled by default).
- Send the generated SRT content when calling the cut or mix endpoints if enabled.

**Total estimated effort:** 4 developer-days
